# Deal Strategy: 城知城市生活知识库的首个试点

## Deal Snapshot

- Account：尚无已确认客户。目标为用户提出的城市部门潜在采购方向。
- Opportunity / Stage / Close Date：均未确定；没有采购承诺、预算或签约事实。
- Time Window：以下以建议的4周小范围试点说明，属于计划，并非已约定日程。
- Run Mode：基于现有产品与用户目标的初始销售路径；判断信心有限。
- Coverage Summary：依据用户需求、已实现代码、公开资料与本地验证记录；没有客户访谈、CRM或真实试点成效。

## Deal Map

定位建议：**把城市公开资料转化成居民、新来者和访客能问、能查出处、能保存行动清单的城市生活服务。** 对外主张聚焦具体能力与已核验范围。

建议先用北京作为深入样板。31城目录适合展示扩展结构，每城当前资料深度不同，不能将它作为“全国城市资料已全量覆盖”的证据。

三个可演示的问题：

1. “刚来北京工作，租住、求职和办事分别先准备什么？”展示不同部门的适用对象，建立生活清单。
2. “父母从外地来住，医保备案和无障碍出行怎么安排？”先分清参保地与就医地，再追溯服务说明。
3. “租房备案、公积金和孩子入学有什么联系？”展示信息复用与资格审核的区别，并提示入学年份。

5分钟演示顺序：生活问题 → 带出处回答 → 打开原文、查看日期和范围 → 收藏与清单 → 管理后台审核发布与纠错 → 本城覆盖及缺口。总目录现已提供该顺序的提示。

现阶段依赖：目标城市主管方尚未访谈、内容仍需扩充、微信尚未发布、模型尚未实调、持续运维与部署尚未落实。“比攻略平台更优越”仍是待验证的产品假设，应通过任务比较取得证据。

试点指标建议（目标待双方商定，以下不是已达到的结果）：回答是否被原文支持；过期或跨城规则误用次数；用户找到正确官方入口的成功率；完成同组生活任务的时间与追加搜索次数；内容从发现变更到核验更新的时长；每周审核工时。与攻略搜索比较时使用同一批任务和用户，保留无法回答、错误及失败记录，不挑选成功案例作为全部结果。

## Evidence Gaps

没有已确认客户、预算、联系人、试点期限、使用人数与采购路径，也没有真实用户对照结果。下一步最小补证是用现有北京样板与目标业务负责人核对20个高频问题，确认是否愿意围绕明确范围试用。

项目能力与验证依据：本目录 `build-results.json`、`http-results.json`；各城 `content/coverage.json`；北京 `server/knowledge.mjs`、`content/national.json` 与照片许可清单。程序运行验证不能替代事实质量验收或客户价值证明。

## Inference Notes

“城市生活服务＋出处追溯”可能比单纯游览介绍更适合持续使用，是基于用户目标和当前产品结构的定位假设；尚无市场或采购反馈验证。建议把后续工作收敛成北京20题的共同验收计划，再讨论合作范围。
